### 02.2 — Motion system & reduced-motion path

**What & why.** This product is mostly motion, so motion is infrastructure, not decoration. This story
defines the shared vocabulary — durations, easing curves, the entrance/exit primitives, the staggering
rule, the glitch treatment — once, so that four scenes built by four separate stories read as one
continuous piece rather than four animations that happen to be adjacent.

It also builds the **reduced-motion path**. On a product where motion carries the whole experience,
`prefers-reduced-motion` cannot mean "animations off" — that would leave a visitor staring at a static
page with no indication anything advanced. It means a *second, calmer choreography*: the flow stays
fully completable, transitions become fades and cuts rather than travel, and nothing that communicates
state is expressed through motion alone ([PDR-003](../../product/decisions.md)).

**Value archetype.** Brand perception (motion consistency is what makes it feel authored) + Enabler
(every scene story consumes these primitives).

**Surface / UX fit.** Cross-cutting — touches all four states of the single surface. Establishes the
motion conventions [PDR-003](../../product/decisions.md) records, which every later story cites rather
than re-deciding.

**Prioritization.** Built before the scenes, alongside 02.1, for the same reason: extracting a shared
motion system *after* four scenes have each invented their own timing is the predictable failure mode of
an animation-led build, and it is expensive to unwind. The owner's "get the UX right, no deadline" call
is what makes doing this properly up front affordable.

**Edge cases — resolved.**
- **`prefers-reduced-motion` enabled.** A real alternate path, not a disabled one. The flow stays
  completable and still feels intentional.
- **State communicated by motion alone.** Prohibited — every state change has a non-motion signal too
  (text, position, or color), so the reduced path never loses meaning.
- **Low-end phones.** Mobile is the primary target, so the motion budget is set against a mid-range
  phone, not a desktop GPU. A dropped-frame experience is a brand-perception failure, not a performance
  nit.
- **The glitch.** Defined here as a reusable treatment, not improvised inside 02.4 — it is the product's
  signature moment and must be specified once.

**Edge cases — deferred.**
- Considered, deferred — honoring a data-saver / low-bandwidth signal as a third motion tier. Reduced
  motion covers the accessibility obligation; a bandwidth tier is an optimization with no evidence yet.

**Acceptance criteria (product-level).**
- A single documented set of durations, easings, and entrance/exit primitives exists, and the scene
  stories use it rather than ad-hoc values.
- The glitch treatment is specified once here and reused by 02.4.
- With `prefers-reduced-motion` set, the entire flow — opening through confirmation — is completable,
  and every state change is still legible.
- No state in the flow is communicated only by movement.
- The flow holds a steady frame rate on a mid-range phone.
